# ADR-002：以数据库条件更新和唯一约束仲裁并发

- 状态：已接受
- 日期：2026-09-15

## 背景

并发接单、重复 SN 和至少一次消息投递都会产生“先读时合法，写入时已变化”的竞争。只做应用层预查询无法关闭这个窗口；JVM 锁也无法覆盖多实例。

## 候选方案

- 先查询后更新：代码直观，但存在 TOCTOU 竞争。
- JVM 或 Redis 分布式锁：能串行化部分路径，但增加锁过期、所有权与可用性问题，数据库仍需要约束。
- 悲观锁：可用，但延长事务和锁等待，不适合只需选出一个胜者的短更新。
- 条件 UPDATE / 数据库唯一键：由实际提交点决定结果。

## 决定

状态迁移使用 `UPDATE ... WHERE id=? AND status=?`，以 affected rows 判断成功或冲突；状态与轨迹同一事务。设备 SN、alarm eventId 和消费结果 eventId 使用唯一约束。应用预查询只作为快速路径，唯一约束是并发最终防线。

## 结果

测试在真实 MySQL 上证明两人并发接单只有一个胜者，两个并发消费者只有一条告警，轨迹异常会回滚主状态。代价是每个业务迁移需要显式 SQL，唯一冲突也必须区分预期重复与其他完整性错误。若未来需要在多个独立数据库间维护同一不变量，本 ADR 不再足够，届时应先重新划分数据所有权，再评估 Saga/Outbox，而不是直接增加全局锁。
