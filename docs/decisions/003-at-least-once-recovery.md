# ADR-003：接受至少一次投递，用业务幂等和恢复记录闭环

- 状态：已接受
- 日期：2026-09-15

## 背景

RocketMQ 收到设备告警后需要写告警、按规则更新设备状态并保存处理结果。Broker ACK 与 MySQL commit 不是同一个原子操作，数据库提交后进程崩溃会使同一消息重投。XXL-JOB 也可能因回调超时或人工触发重复执行。

## 候选方案

- 分布式事务 / Exactly-once 宣称：系统复杂且仍不能替代业务幂等。
- Redis 去重：过期和数据丢失后无法作为审计最终证据。
- MySQL 结果记录、唯一约束和重复安全处理：额外占用表与索引，但结果可查询、可恢复。

## 决定

告警以 eventId 为不变业务键，预查询成功记录，落库事务同时写 alarm、设备变化和 PROCESSED 结果。业务坏消息留档后 ACK；系统失败在独立事务记录后抛出。人工修正保持 eventId 并重走同一入口。巡检使用 timeout flag 条件更新与 SYSTEM 轨迹，重复执行排除已完成项。

## 结果

重复、并发、坏消息、系统重试和人工重放均可从数据库解释。代价是结果表、失败表和恢复接口的维护，并且处理是“业务最终一次”而非运输层 exactly-once。只有跨数据库写入成为真实需求时才评估 Outbox/Saga；当前本地事务内没有这个问题。
