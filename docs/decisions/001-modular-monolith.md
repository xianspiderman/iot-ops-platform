# ADR-001：使用模块化单体作为部署边界

- 状态：已接受
- 日期：2026-09-15

## 背景

项目同时包含基础数据、设备、工单、告警、巡检与权限。它们有清晰业务边界，但工单创建、设备关系和轨迹等操作需要本地强一致。当前没有独立团队所有权、差异化扩容或故障隔离数据。

## 候选方案

1. 一个无边界的单体：启动简单，但容易让 Controller、Service 和表关系相互渗透。
2. 按业务能力分包的模块化单体：一个进程与数据库，边界由包和服务 API 保持。
3. 微服务：每个能力独立部署，需要服务发现、远程调用、跨服务一致性和更多观测设施。

## 决定

采用模块化单体。`auth`、`project`、`product`、`device`、`workorder`、`alarm`、`timeout`、`audit` 作为能力包；外部 RocketMQ listener 和 XXL handler 只是业务服务的适配器。需要一致性的更新使用 MySQL 本地事务。

## 结果

收益是启动、调试、测试和事务边界直接，Docker 只构建一个后端镜像；代价是所有模块共同扩缩容和发布。只有某个模块出现可测的独立吞吐、可用性或团队边界需求，并能定义数据所有权与失败协议时，才考虑拆分。拆分前优先用模块测试和包依赖保持边界。
